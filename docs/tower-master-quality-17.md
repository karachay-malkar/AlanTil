# Техническое задание: AlanTil Tower — Master Quality Specification

**Основа:** `karachay-malkar/AlanTil`, ветка `17.0`, коммит `8258ac82fa00a9de14373f6da77c3b0d2d24474a` (11.10.2026).  
**Статус:** принято к реализации пользователем 11.10.2026; работа ведётся по этапам с отдельной фактической приёмкой.  
**Цель:** довести существующую браузерную 3D-игру строительства башни до законченного уровня игрового продукта, не ограничиваясь косметическим редизайном.

## 1. Фактически установленная исходная архитектура

Проверены: `src/features/tower/index.js`, `scene.js`, `tower.css`, `repository.js`, `packages/tower-game/core.mjs`, `assets/tower/processed-rocks.mjs`, документы `docs/tower-*`, тесты башни, скрипт браузерной QA. **Свежая визуальная оценка через запущенный браузер на данном HEAD не проведена; описание текущих недостатков опирается на код, а не выдаётся за результаты живого плейтеста.**

- WebGL/Three.js; игровое поле — сетка `60 × 60`, шаг 25 см, предельная высота 80 ячеек.
- Камни четырёх типов. 23 обработанные вариации из переданного `fbx.glb`: обычные — 7, средние — 5, вытянутые — 4, большие — 7. Изображаемые камни сейчас масштабируются из нормализованных мешей по габаритам ячеек.
- Остальные объекты: балка, настил, окно, дверь, лестница, крыша. Цены и допустимые размеры описаны в `core.mjs` и проверяются сервером.
- Сохранение в Supabase: ревизии, атомарные операции, идентификатор операции, точный возврат уплаченной валюты, запрет дублирования списания. Для гостей строительство за валюту недоступно.
- Есть размещение полупрозрачной копии, выбор/удаление, категории каталога, горизонтальная прокрутка, разрез по уровню, управление камерой. Код всё ещё содержит множество технических элементов и окон настройки.
- Критические пробелы: поворот камня меняет дискретное поле `rotation` без плавного визуального вращения; при визуализации каменных мешей поворот по Y не применяется как реальный поворот модели — меняются габариты масштабирования. Автоматической генерации мелких камней в стыках нет. Проёмы не имеют полноценной системы сопряжения с окружающей кладкой. Отображение башни целиком перестраивается при обновлении элементов; нет инкрементального генератора швов. Браузерные тесты не доказывают художественное качество и удобство каждого жеста.

## 2. Образ продукта и ограничения

**Образ:** тихая, тактильная, исторически вдохновлённая строительная игра: камни воспринимаются тяжёлыми, естественными и материальными; пользователь наслаждается построением башни, а не управлением редактором координат. Эстетический ориентир — каменная архитектура Верхней Балкарии и окружающий горный ландшафт. Использовать фотографии реальных сооружений как проверяемые визуальные референсы; не представлять фантазийные детали как точную историческую реконструкцию.

**Обязательные принципы:** 3D-сцена занимает почти всё окно; валюты — вверху; минимальный каталог — снизу; второстепенные действия — контекстно и по требованию; мобильное управление равноправно десктопному; выраженная физическая правдоподобность при отсутствии необходимости в дорогостоящей физической симуляции.

**Без изменения согласованных правил:** виды камней и диапазоны размеров, фиксированные цены по типу, обмен 1 золото = 8 серебра, ограничения сохранений, авторизация, правила получения наград и существующие башни. Новые декоративные мелкие камни не являются покупаемыми объектами. Любое изменение этих правил — только отдельным утверждённым ТЗ.

**Не входит в данную итерацию:** PvP, свободная физика обрушений, новые словари, новые способы монетизации, перестройка общего интерфейса AlanTil, нативный игровой движок. Не добавлять усложнения ради эффектной демонстрации.

## 3. Технический принцип: три независимых слоя

1. **Authoritative Build Model**: исходные элементы `{id,type,x,y,z,sx,sy,sz,rotation,variant,...}`, ограничения, коллизии, поддержка, цены, ревизии, серверные транзакции. Истина — только в данных Supabase; существующие записи должны читаться без миграции.
2. **Derived Masonry Presentation**: визуальные меши, ориентации, сопряжения, фасадные швы, мелкие камни, тени, LOD. Генерируется детерминированно из авторитетного снимка, не влияет на кошелёк, валидатор и серверный JSON, не является интерактивной покупкой.
3. **Interaction & Feedback**: единая машина состояний ввода, умное позиционирование, каталог, HUD, камера, анимации, звуки, ошибки, доступность и сохранение.

Не допускать второго источника истины: визуальное положение камня после завершения анимации должно строго соответствовать серверной модели. Не переписывать SQL-проверки на стороне клиента. Не менять RPC-контракт, пока не доказана необходимость.

## 4. Качественная дизайн-система (все элементы без исключения)

Создать один набор токенов: фон и поверхности, пять семантических цветов (основной, нейтральный, подтверждение, предупреждение, ошибка), состояния кнопок, типографика, иконки, отступы, высоты, радиусы, тени, анимационные кривые. Отказаться от разрозненных Unicode-символов как единственных игровых иконок. Каталог использует **изображения реальных игровых 3D-объектов** с одинаковой камерой, масштабом, светом и фоном; цена всегда визуально однозначна.

- Одна главная кнопка активного действия; второстепенные — менее контрастные. Единообразные `idle / hover / focus / active / selected / disabled / loading / success / error`.
- Сенсорные зоны частых действий — не меньше 44×44 CSS px; достаточные промежутки, видимый `focus-visible`, удобная работа одним пальцем.
- Основные подписи на мобильном — целевой минимум 14 px; вспомогательные не меньше 12 px при проверенном контрасте. Исключить микротекст 10–11 px для важных действий.
- Запрещены разнотипные псевдотени, чрезмерное стекло/blur, мелкие технические пояснения на сцене, плашки без функции и перекрывающие друг друга элементы.
- Все слои HUD учитывают safe-area, экранную клавиатуру, низкую высоту окна, браузерное масштабирование и отсутствие hover.
- Перед внедрением зафиксировать 4–6 эталонных состояний интерфейса (скриншоты работающей игры): пустой участок; выбран камень; недопустимая установка; готовая кладка; выделен существующий объект; открыта панель настроек.

## 5. Экран и навигация

**Верх:** возврат в AlanTil с сохранением навигационного контекста; компактный и постоянно читаемый баланс серебра и золота; индикатор незавершённой серверной операции только когда он действительно нужен. Не добавлять постоянный заголовок/размер сетки поверх сцены.

**Центр:** единственная доминанта — башня; контекстная подсветка места установки; ненавязчивый указатель осей только при точной настройке. Нет постоянно видимой технической сетки поверх природного ландшафта; сетку показывать по необходимости, с плавным исчезновением.

**Справа:** максимум 1–2 постоянно доступных контекстных элемента (например, «показать всю башню» и режим обзора). Вращение и масштабирование камеры — прежде всего естественными жестами. Остальные кнопки камеры в раскрываемом наборе либо только на десктопе при доказанной полезности.

**Снизу:** док-каталог с горизонтальной прокруткой и карточками объектов: миниатюра, название, цена, индикация выбранного. В обычном раскрытом состоянии занимает не более ~20% высоты типичного мобильного экрана; развёрнутая панель настроек — не более ~32% с внутренней прокруткой. Свернуть одним действием; при жесте строительства не перехватывать обзор. Переключение категории сохраняет положение каталога либо явно сбрасывает прокрутку на начало категории, без случайного смещения.

**В контексте установки:** одна заметная кнопка «Установить», короткая цена, доступные «Повернуть» и «Отмена» непосредственно возле рабочего действия, но не поверх устанавливаемого камня. «Размеры / точное положение / валюта / разрез / обмен» — во вторичном раскрываемом инструменте, не в основном игровом потоке.

**В контексте выбора построенного:** короткое название, доступное действие удаления и точная сумма возврата; при наличии зависимых элементов объяснять причину запрета; не открывать режим построения автоматически.

## 6. Машина состояний и управление без конфликтов

Вместо распределённых событий в `index.js` внедрить централизованный контроллер состояний:
`idle → catalog-selected → preview-positioning → preview-valid / preview-invalid → submitting → placed / rejected`, независимо ветка `inspecting → selecting → removing`, а также `loading`, `read-only`, `offline`, `context-lost`. Для каждого перехода определить допустимые события, показ кнопок, блокировку покупок и поведение отмены.

- **Касание карточки:** выбор материала, появление полупрозрачного камня, без траты валюты.
- **Перетаскивание карточки:** перемещение призрака с привязкой к поверхности; на отпускании — позиция зафиксирована как предварительная, **не покупка без подтверждения**. Горизонтальный свайп каталога всегда прокручивает каталог, а не переносит камень.
- **Касание / перемещение в сцене:** тап размещает призрак; короткий drag по пустой сцене управляет камерой; при активной манипуляции камнем — перемещает только камень. Между режимами не должно быть неоднозначности. Второй палец немедленно переключает жест на камеру и исключает ложную установку.
- **Поворот объекта:** крупная контекстная кнопка; на ПК также клавиши Q/E; на мобильном опционально контекстный жест двумя пальцами только после UX-проверки, не конфликтующий с вращением камеры.
- **Камера:** drag/orbit, pinch/wheel zoom, фокус на объекте, «вся башня». Touch/pointer capture и отмены учитывают `pointercancel`, выход за границы окна, входящие системные жесты.
- **Клавиатура:** Esc отмена/закрытие; Enter подтверждение при допустимом preview; Delete удаление выделенного элемента с защитой; стрелки точной корректировки только в режиме точного позиционирования. Нельзя выполнять действие во время ввода в текстовое поле.
- **Удаление:** отсутствие случайного удаления одним тапом; подтверждение для необратимо значимого действия, но не для каждого безопасного технического взаимодействия. Если реализуется Undo, оно обязано создавать корректную обратную серверную мутацию, а не притворяться локальным откатом.

Система ввода должна быть покрыта матрицей событий и автотестами: одиночный тап, двойной тап, длинное удержание, свайп дока, перетаскивание, drag сцены, pinch, два пальца с разным временем касания, быстрое переключение инструментов, отмена, поворот экрана, смена вкладки.

## 7. Умное позиционирование и единая кинематика камня

1. Хит-тест определяет контакт с **логической поверхностью** объекта, а не случайным выступом грубой треугольной модели; нормаль преобразуется в мировые оси и проверяется логическим валидатором.
2. Предлагать ближайшую допустимую привязку на поверхности и рядом с соседними гранями, но только в ограниченном радиусе; не переносить камень далеко без ведома игрока. Если подходящего места нет — показывать исходное положение с понятной причиной ошибки.
3. Показывать потенциальный контакт и опору (короткая подсветка), не заставляя вручную вводить X/Y/Z. Точный ввод сохраняется как профессиональный режим.
4. Поворот изменяет **реальный видимый 3D-меш** вокруг своего центра, а не только его AABB. Для четырёх ориентаций камня — дискретный игровой шаг 90°; анимация 180–260 мс с мягким ускорением/торможением, сохранением опорной точки и корректным изменением габаритов в момент завершения. Быстрые повторные нажатия должны вести к предсказуемой конечной ориентации без рывков или накопления некорректных tween.
5. При смене стороны укладки или масштаба призрак не мигает, не пропадает за камерой, не дрожит при переходе через соседние пиксели.
6. Призрак использует тот же меш, силуэт и ориентацию, что конечный объект; допустимость — одновременно цветом и понятным значком/сообщением. Недопустимая установка невозможна даже при быстрой серии кликов.
7. Анимация утверждённой установки 250–450 мс: объект получает материальность, минимальное оседание к опоре, мягкая локальная пыль/контактный звук; без мультяшного отскока. Анимация запускается после подтверждения серверной операции. Пока сервер отвечает — сохраняется прозрачная версия с индикатором ожидания; при ошибке — не появляется оплаченный камень.
8. Удаление имеет короткую обратную анимацию после подтверждённого сервером возврата; обновление баланса синхронизировано с событием, не с таймером.

## 8. Главная новая система: автоматическая забутовка мелкими камнями

**Требуемый результат:** при укладке крупных/средних/вытянутых/обычных камней узкие физически правдоподобные просветы между соседними неровными поверхностями автоматически заполняются небольшими камнями и клиньями. Башня выглядит как кладка, а не как набор отдельных low-poly мешей.

**Не путать:** зазор между рельефными гранями, конструктивный оконный/дверной проём, внутреннюю полость башни и пустое место, куда игрок ещё намерен положить полноценный камень. Автоматическая забутовка касается только малых швов, а не строит стену вместо игрока.

**Алгоритмический контракт:**

1. Построить пространственный индекс (чанки, adjacency/соседние bounding volumes) по авторитетным элементам. Учитывать их поворот, локальные нормализованные формы и реальные габариты.
2. Для затронутого чанка выявить только **реальные просветы между визуальными поверхностями** смежных камней через предрасчитанные облегчённые оболочки/локальное distance sampling. Не использовать глобальную плотную 3D-вокселизацию всей площадки.
3. Классифицировать щели: кандидат на забутовку, конструктивный проём, открытая внешняя грань, пустой внутренний объём, незначительный визуальный шов. Стартовый целевой диапазон для локальной забутовки — порядка 2–15 см; параметры подобрать на визуальных тестах относительно размера основных блоков, не превращая швы в регулярную сетку.
4. Для кандидата — выбирать 2–5 типов мелких неровных мешей, ориентацию, размер и количество по локальной геометрии. Камни выглядят вставленными в шов, слегка утопленными, а не наклеенными поверх стены. Допуск на контакт — без заметного проваливания сквозь соседние меши и без z-fighting.
5. Генерация детерминированная по данным башни, координате локального шва, идентификаторам соседних элементов и `infillAlgorithmVersion`. Идентичный снимок на разных устройствах даёт идентичную композицию; повторная загрузка не меняет рисунок произвольно.
6. После добавления/поворота/удаления основного камня пересчитываются только затронутые соседние чанки. Незатронутые швы не «прыгают» и не меняют внешний вид. Обновление атомарно для визуального слоя.
7. Генерируемые камни **не имеют цены, отдельного ID покупаемого объекта, server mutation, hit-test, коллизии или несущей роли**. Не учитываются в лимите 10 000 основных элементов. Для выбора под ними возвращается ближайший основной строительный элемент.
8. Разрез/скрытие слоёв распространяется на забутовку; при выключении и включении слоя композиция не меняется.
9. При ограничении производительности постепенно сокращать детализацию/количество видимых мелких камней в дальнем плане (LOD), не разрушая близкий силуэт швов. Результат батчить через `InstancedMesh`, по материалу/LOD.
10. Особо проверять случаи: вертикальный шов, горизонтальный шов, Т-образное соединение, внешний и внутренний угол, верх стены, опора балки, границы настила и нижние края проёмов; нельзя автоматически закрывать оконную/дверную пустоту и проход.

**Обязательный визуальный тест:** образец стены с 100–200 основными камнями, четырьмя видами крупных камней, неодинаковыми швами, углом и настоящим проёмом — до/после забутовки, четыре ракурса, крупный план. Ни один декоративный камень не должен зависеть от порядка размещения основных элементов, если финальная авторитетная геометрия одинакова.

## 9. Объекты и подлинные проёмы

- Все основные камни: единая система масштаба и качества нормалей, 23 исходных варианта сохранить; визуальная ориентация должна соответствовать сохранённому повороту. Не растягивать исходные текстуры/контуры так, чтобы камень превращался в резиновый блок; подготовить подходящие варианты геометрии для крайних допустимых пропорций.
- Формировать кладку со смещением стыков естественным выбором камня игроком; подсказка о перекрытии вертикальных швов может быть ненавязчивой, но не заменять выбор игрока автопостройкой.
- **Окно:** геометрия действительно содержит проходящее световое отверстие, а не нарисованный прямоугольник на сплошном блоке. Окружение из камней корректно примыкает к бокам, низу и перемычке; автоматическая забутовка не перекрывает световой проход. Существующая серверная логическая коробка резервирует габариты модуля, поэтому совместимость с текущим валидатором сохраняется.
- **Дверь:** реальный портал, видимые косяки и притолока, при наличии дверного полотна — отдельная визуальная деталь. Не допускать «дверь, висящую в сплошной стене», либо вводить понятное правило подготовки пустого проёма в игровой геометрии.
- **Дерево:** балка, настил, лестница и крыша требуют геометрически убедительных деталей крепления и продуманного соединения с кладкой; не использовать случайные кубы вместо визуальной разработки. Визуальные улучшения не расширяют несовместимо hitboxes.
- Историческая достоверность: отдельный набор фото-референсов башен Верхней Балкарии с пометками, какие решения подтверждены, какие художественно адаптированы.

## 10. Камера, свет, материалы и окружение

- Камера: OrbitControls как основа можно сохранить, но поверх — контроллер плавных целевых позиций и ориентаций (кадрирование, фокус на поставленном элементе, умный `home` с учётом высоты башни и экрана). Плавные переходы 300–650 мс; допустима отмена в любой момент ручным жестом. Избежать прохождения камеры через кладку, чрезмерного приближения и потери башни из кадра.
- Целевой объект не должен перекрываться нижним доком и правыми элементами; при выборе верхних ярусов фокус смещается по высоте. Управление остаётся одинаковым при 0, 1 000 и 10 000 элементах.
- Материалы: единая цветовая гамма местного камня с естественными вариациями, шероховатостью и нормалями; без пластмассового блеска, случайных кислотных оттенков и повторяющихся очевидных паттернов. Корректное цветовое пространство, освещение PBR и проверка тонемаппинга.
- Свет: мягкий направленный солнечный свет, читаемый рельеф и контактные тени; сбалансировать с производительностью. Не допускать мерцания, жёстких теневых лестниц и теней в неправильном направлении.
- Окружение: аккуратная площадка в горном ландшафте, выверенная дальняя перспектива и воздух. Горы поддерживают чувство места, но не отвлекают; текущие плоские полосы хребтов — заменить более проработанной компактной композицией по реальным референсам, не обещая точной географической реконструкции.
- Эффекты: ограниченная пыль при контакте, тень призрака, очень тонкий визуальный отклик; никаких непрерывных ярких частиц, чрезмерного bloom, тряски камеры или анимации кошелька, мешающей строительству.
- Аудио: тихие качественные разные звуки для камня, дерева, поворота и успешной установки; mute-настройка, соблюдение браузерной политики воспроизведения. Отсутствие звука не влияет на смысл взаимодействия.

## 11. Надёжность, экономика, сохранения

- Продолжать применять существующие `get_tower_snapshot` и `mutate_tower`, ревизии и UUID операций; запрет на повторное списание при потерянном ответе. Все визуальные производные восстанавливать локально из снимка.
- Не показывать положенную покупку до серверного подтверждения. При долгом ответе показывать нейтральное ожидание без блокировки управления камерой. При потере связи — сохранить повторяемую операцию, не выдавать ложное «сохранено»; восстановить по тому же operation ID.
- При конфликте ревизии — явный диалог обновления, без скрытого двойного списания/повторного размещения. Защита от двойного нажатия «Установить».
- Гость: можно осмотреть сцену и каталог; нельзя имитировать реальную оплату. Просмотр чужой башни — без операций изменения и без раскрытия чужого баланса.
- При уходе со страницы: незавершённая транзакция не должна превращаться в потерянную валюту или полусохранённую геометрию. Повторное открытие восстанавливает корректный итог.
- Проверить реальные роли, RLS/RPC, прямой доступ к балансам и публичные разрешения при любых новых серверных изменениях. Для существующего серверного контракта миграция не требуется, если новый слой сугубо визуальный.

## 12. Производительность как часть дизайна

- Не перестраивать все инстанс-группы и не пересчитывать все швы при любом одиночном добавлении/удалении. Ввести chunk dirty flags, переиспользование geometry/material/texture, кэширование и incremental update.
- Использовать instancing для повторяющихся камней, забутовки и элементов декора; LOD/ограничение теней на дистанции; ограничение pixel ratio по профилю устройства.
- В обычном статическом состоянии предпочитать рендер по необходимости (при смене состояния, управлении камерой, анимации, подгрузке), а не бесконечный холостой цикл GPU. Во время камерного damping/анимации рендер продолжать до завершения.
- Сбор метрик без приватных данных: время первого отображения, FPS/p95 frame time, длительность local preview update, пересчёт dirty chunks, WebGL draw calls, JS heap/GPU resource leaks, ошибки загрузки, context lost.
- **Приёмочный ориентир:** стабильная цель 60 fps на выбранном десктопном контрольном устройстве и 30 fps на согласованном среднем реальном смартфоне при строительстве типичной насыщенной башни; в сцене с 1 000 и 3 000 основных элементов фиксировать p95 времени кадра, а при лимите 10 000 обеспечивать управляемое снижение качества вместо зависания. Цифры не считать достигнутыми до инструментального измерения на указанных устройствах.
- При повторении «открыть игру → построить/удалить → выйти» не растут бесконечно текстуры, геометрии, event listeners и GPU-память. WebGL context-loss корректно восстанавливает сцену без повторной оплаты.

## 13. Доступность и адаптация

Разрешения для обязательной проверки: 320×568 (малый мобильный), 390×844 (обычный мобильный), 768×1024 (планшет), 1280×800 и 1440×900 (десктоп); портрет и альбомная ориентация там, где применимо. Дополнительно — мобильный Chrome на реальном Android и Safari на реальном iOS, хотя бы по одному устройству каждого класса при наличии доступа.

- Нет горизонтального переполнения, скрытых важных кнопок и перекрытого confirm; bottom safe-area; доступность при 200% browser zoom.
- Реальная клавиатурная навигация по элементам UI, семантические кнопки, роли/метки для управления камерой, доступные сообщения статуса. Игровые жесты имеют альтернативные явные кнопки.
- `prefers-reduced-motion`: мгновенные либо сокращённые переходы без потери состояния; настройка отключения звука.
- Запрет на информирование исключительно цветом: ошибка preview дублируется значком и короткой причиной, состояние сохранения — текстом.

## 14. Предписанные тесты и автопроверки

1. **Unit:** bounds, collisions, support, currency, encode/decode, повороты 0–3 (балка 4–5), сохранение вариантов из всех 23 мешей.
2. **Property-based/invariants:** генерация швов детерминирована, не создаёт элементов в проёмах, не меняет authoritative model, ограничена бюджетом и остаётся без утечек при произвольном порядке построения.
3. **Geometry visual:** сравнение реальной ориентации 0/90/180/270, экстремальные допустимые пропорции, нормали, углы, силуэты, shadow acne, z-fighting, близкие швы.
4. **Input E2E:** полный набор pointer/touch/keyboard сценариев; тап после pinch не ставит камень; свайп каталога не прокручивает сцену; drag сцены не вызывает оплату; двойное подтверждение создаёт одну мутацию.
5. **Backend:** повтор одинакового operation ID, таймаут сети, конфликт ревизии, недостаточно валюты, реальный возврат, guest/read-only/own account, запреты RLS.
6. **Navigation:** вход/выход из игры не ломает AlanTil, шапку, back, состояние приложения, незавершённый платёж, другие игры.
7. **Render/performance:** 0 / 100 / 1 000 / 3 000 / 10 000 основных элементов, малая и плотная кладка, разрез, длинная сессия, слабое устройство, context lost/resume.
8. **Screenshot/video diff:** эталонные 6+ состояний на пяти разрешениях с контрольными ракурсами; изменения сравниваются пиксельно и экспертно, не только «тест зелёный».
9. **Экспертный adversarial review:** отдельные проверки в ролях game UX designer, technical artist, 3D programmer, accessibility tester, performance engineer, QA. По каждому обзору сохранять обнаруженные дефекты и факт исправления.
10. **Real playtest:** выполнить сценарий «с нуля построить первый ряд → стену → окно → следующий ярус → повернуть камни → заполнить швы → удалить камень → восстановить после перезагрузки» мышью и касанием, с записью экрана.

**Отдельное правило:** тесты, проверяющие только наличие CSS-класса или строки исходного файла, не заменяют реальную функциональную или визуальную проверку.

| Этап | Итог | Что доказывает завершение |
|---|---|---|
| 0. Базовая диагностика | Исходные скриншоты/видео, список дефектов P0–P3, архитектурная карта | Чётко отделены подтверждённые проблемы от предположений; проверен текущий HEAD и рабочий запуск |

| 3. Механика призрака, snap и поворот | Реальное вращение мешей и плавное размещение | 23 варианта, 4 поворота, серия быстрых команд и разные опоры проверены |

Каждый этап: сначала проверка зависимостей и тестов, затем реализация, сравнение с эталоном, независимое выявление дефектов, исправление, повторная проверка. Не объявлять этап завершённым по факту написания кода. Следующий этап не должен скрывать дефекты предыдущего.

## 16. Критерии окончательной приёмки (release gate)

**Нельзя объявить «готово», пока одновременно не выполняются все пункты:**

- Нет открытых P0/P1-дефектов; все P2, влияющие на основное строительство, устранены. Непроверенная функция = неготовая функция.
- Реальный рабочий E2E проходит весь путь строительства на desktop и mobile, включая медленный ответ сервера, отмену, ошибку и повтор входа.
- Все 23 камня отображаются корректно, реально поворачиваются и физически правдоподобно сочетаются; мелкая забутовка заполняет только нужные швы; окна и двери сохраняют отверстия.
- Ни одного случая ложного списания, повторной оплаты, локально «сохранённого» неподтверждённого камня и утраты построенных ранее башен.
- Баланс, основные цены, размеры, авторизация, остальные разделы AlanTil и навигация регрессионно работают.
- Реальные скриншоты и короткие видеозаписи подтверждают внешний вид каждого состояния и каждую ключевую анимацию; проверки только исходного кода недостаточно.
- Измерены FPS, p95 frame time, время восстановления после потери контекста и отсутствие долгосрочных утечек на согласованных устройствах; если показатель не достигнут, этот пункт честно обозначен как незакрытый.
- Есть итеративный журнал «проблема → воспроизведение → исправление → подтверждение», включающий самостоятельно найденные дефекты; требуется минимум два отдельных прохода самостоятельного UX/визуального аудита **после** функциональной реализации.
- Обновлены документация и QA-сценарии. Полные изменённые файлы и итоговый ZIP с размерами файлов передаются только по завершении реализации; git commit/push — после реального QA, без заявления о деплое до проверки опубликованной версии.

## 17. Требуемая организация работы исполнителя

Исполнитель обязан действовать как продуктовая команда с несколькими независимыми дисциплинами, а не ждать пользовательских замечаний по мелочам. После каждого этапа проводить внутренний цикл: **самостоятельно обнаружить слабости → ранжировать по важности → исправить первопричины → протестировать → заново оценить целиком**. Проверять весь пользовательский путь, а не только последние изменённые кнопки. Если эстетическое решение не работает, переделывать его до релизного шлюза, а не отправлять как «почти готово».

Любая функция оценивается сразу по пяти сторонам: понятность, материальная достоверность, предсказуемость взаимодействия, производительность, устойчивость данных. Инновации допускаются только если улучшают эти критерии; усложнение ради усложнения запрещено. При отсутствии инструментального подтверждения честно указывать ограничение, а не выдавать допущение за завершение.

**Следующее действие после утверждения этого ТЗ:** отдельный файл implementation plan с точными изменяемыми функциями/модулями, зависимостями и тест-кейсами на каждый этап. Код до утверждения ТЗ не менять.
