# AlanTil 17.3: joint-aware authored-stone section rendering

Base: 17.2 (7163257). This update changes presentation geometry only, not purchases, server physics, wallet or saved V2 elements.

## Implemented

- `solveMasonryLayout` computes one deterministically staggered partition of the union of up to 250 authoritative section envelopes, not separate independent box grids. Stones can cross purchased section boundaries; the stone mesh comes solely from the authored 23-mesh `ROCK_PACK`.
- Vertical interlocking joins selected exactly matching lower/upper envelopes into single physical authored-rock render models. `validateCombinedLayout` confirms the partition's rectangular *envelopes* fully cover the union without overlap and that source models are not modified. This is not a mesh-penetration proof.
- `findSectionJoints` recognizes bridging stones. `section-pipeline` calls the global solver once and batches visual meshes back to owning sections. Stone variants are chosen using the source mesh vertex outline distribution, with deterministic variation.
- Contact adaptation for section rendering is capped at 0.12 cell (= 3 cm) and one refinement pass. The original source indexed mesh remains the only source of triangles; additional contact triangles are refined from those triangles, not separately generated block models.
- Worker sends geometry first, then computes small authored-rock infill asynchronously and sends it independently. Infill failure does not delete the already built section geometry.
- Mobile geometry budget: 20,000 infill triangles; desktop: 48,000. Both have finite fragment/joint ceilings. Previous full re-tessellation could generate over 160,000 large-rock triangles; single refinement limits excessive GPU memory use.
- A separate `sectionInfillReady` marker and bridge count support browser QA. Four-section desktop/mobile snapshots are collected by the existing GitHub Actions workflow.

## Compatibility/safety

- Do not migrate paid V2 stones to V3 or change `mutate_tower_v2` semantics. Authored section pieces are not persisted independently or purchasable individually. A server-authoritative V3 with per-section prices, authenticated transactions, support tests and idempotent revisions remains necessary before physically authoritative section-building gameplay can be claimed.
- Source FBX/GLB contains 36 geometries but the existing `ROCK_PACK` and Supabase V2 shape catalogue use 23. The 13 unintegrated shapes were NOT inserted without validating source-to-variant correspondence and server cost/physics. Inserting them blindly would invalidate existing shape IDs.
- The wall's structural envelope cover does **not** imply collision-free 3D surfaces, sufficient load-bearing contact patches, 4 cm maximum visible gap, or completion of all strict visual design targets. These require pixel/mesh QA and V3 physics work.

## Tests

- `node --test tests/tower-*.test.mjs`
- `node scripts/qa/browser-tower-section-17-2.cjs` in a Chromium-installed environment. The fixture asserts sections, bridges, infill, WebGL and absence of client JS errors.
- `tests/tower-section-global-layout-17-3.test.mjs` asserts determinism, no envelope overlap, full coverage, horizontal and vertical bridging, order independence, compatibility with isolated sections and source mesh immutability.
